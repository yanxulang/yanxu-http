# 安全模型

## 保护目标

1. 在应用处理前唯一确定 HTTP 消息边界；
2. 限制不可信输入导致的读取、循环和内存消耗；
3. 阻止首部/响应注入、重复关键首部歧义和常见请求走私；
4. 保持 Cookie 与 WebSocket 升级的安全默认值和所有权边界；
5. 让调用方通过稳定错误代码采取一致策略。

## 已实施控制

- 严格 CRLF，请求行恰含方法、目标和`HTTP/1.1`；拒绝折叠首部、NUL、非法 token 与控制字符；
- HTTP/1.1 必须有且只有一个有效 Host；规范化端口和方括号 IPv6；
- `Content-Length`只接受规范十进制，重复值、逗号值和与`Transfer-Encoding`并存均拒绝；
- 请求分块只接受单一最终`chunked`，验证块大小、扩展、CRLF、累计正文与尾部禁用字段；
- 解析预算覆盖请求行、首部、正文、分块、尾部、Cookie、查询、表单和会话寿命；
- 响应首部拒绝 NUL/CR/LF，编码器独占 framing 与连接首部；无正文状态和 HEAD 语义单独验证；
- Cookie 使用保守字符集，并验证`SameSite=None`、`Partitioned`、`__Host-`和`__Secure-`组合；
- WebSocket 要求 GET、HTTP/1.1、规范 16 字节密钥、版本 13、明确 Upgrade token、无 HTTP 正文与无 close；Origin 由显式允许列表决定；
- 101 只能通过会话升级方法发送，超前读取字节不会丢失或被旧所有者继续消费。

## 信任边界

本库不验证代理添加的`Forwarded`或`X-Forwarded-*`，不判断客户端真实地址，也不提供 TLS。应用只能在已配置可信代理范围内解释转发首部。认证、授权、CSRF、Session 签名、请求并发、速率限制、日志脱敏和审计属于上层责任。

请求对象的首部、查询和 Cookie 快照不代表数据可信；它们只代表语法和 framing 已验证。文件名经过`安全文件名（）`处理后仍应由应用生成最终存储名，不能直接控制路径。

## 连接失败策略

一旦请求行、首部、正文或分块 framing 失败，调用方应关闭连接，因为后续字节边界不再可信。应用错误若发生在完整请求解析之后，可以发送错误响应，但应根据`请求.必须关闭（）`和会话状态决定是否复用。

升级成功后，`HTTP升级通道`成为套接字唯一所有者。调用方必须实现所选上层协议的帧、消息、关闭、心跳、压缩和资源限制；本库的握手成功不表示这些部分已受保护。

## 不在 1.0 范围

TLS、HTTP/2、HTTP/3、WebSocket 帧、扩展协商、慢连接全局调度、磁盘上传隔离、反向代理、WAF 和应用沙箱均不在本库范围。相关风险不能通过提高本库预算来消除。
